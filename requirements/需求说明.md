# AI 面试助手 — 需求说明

> 本文档只记录**需求**，不含技术实现方案。
> 状态：需求已确认（仅剩 1 项低优先级待定）
> 建立日期：2026-10-15 ｜ 最近更新：2026-10-15

---

## 一、项目背景与目标

做一个本地可运行的 AI 模拟面试助手，帮助候选人用接近真实面试的方式检验自己的水平。

核心流程：**上传一份简历 → 大模型解析简历并据此建立候选人画像 → 围绕该画像进行一场模拟面试 → 给出总结评分与改进建议。**

与市面上"陪聊式"AI 面试工具的关键区别：**评价必须真实，不迎合用户**。工具的价值在于暴露问题，而不是提供情绪价值。

---

## 二、功能需求

### FR-1 简历上传与解析建像

**原始需求**
> 项目主流程为上传一份简历，由大模型解析建立并进行面试。

**需求描述**
- 用户上传一份简历文件。**首期只支持 PDF**，不做其他格式，也不做"粘贴文本"兜底。
- 系统调用大模型解析简历，**提取全部文字内容**，并从中整理出结构化画像，作为后续面试提问的依据。
- 面试提问必须基于该画像展开，而不是脱离简历的通用问题。

**画像需提取的内容**
- 目标岗位
- 项目经验
- 工作经验
- 技术栈
- 工作年限
- 自我评价
- 其他简历中常见的常规内容（教育经历、获奖、证书等）

**验收要点**
- 上传 PDF 后能看到解析出的结构化画像，上述字段齐全。
- 后续面试中的提问能对应到简历里的具体项目与技术。

---

### FR-2 面试过程支持候选人语音作答

**原始需求**
> 面试过程支持面试者语音。

**需求描述**
- 候选人在面试过程中可以用语音回答问题，不必只能打字。
- 语音转文字后进入对话，作为本次作答内容。

**验收要点**
- 语音作答内容能正确转成文字并出现在对话记录中。
- 语音与键盘输入并存，候选人任何时刻都能改用打字。

**已确认**
- 面试官（AI）一侧**不需要**语音输出，纯文字。

---

### FR-3 面试难度分五档

**原始需求**
> 可设置面试难度，分五档难度。

**需求描述**
- 面试开始前选择难度，共 **5 档**，对应市面上对工程师的常见定位。
- 不同档位对应不同的提问深度与追问力度，需有明显可感知的差异，而不是只改一个标签。

**各档定位**

| 档位 | 定位 | 面试官侧重 |
|---|---|---|
| L1 | 实习生 | 问学习情况、课程基础；在意学校活动、动手经历、学习能力与态度 |
| L2 | 初级工程师 | 能独立负责单模块开发，有一定解决问题能力；看重工作中实际接触的知识内容 |
| L3 | 中级工程师 | 同上，但要求更扎实 —— 需能说清原理与取舍，而不只是"用过" |
| L4 | 高级工程师 | 能从零做一个项目、全流程清楚；问架构居多，追问更深 |
| L5 | 行业专家 / 产品架构师 | 不再只考技术：看在该领域是否做成过**成功的产品**，能否做**产品层面的架构思考**与**行业层面的思考**；关注**开源参与**、**多年行业沉淀**、能否沉淀出**通用行业解决方案** |

**L5 的考察维度（区别于其他档的关键）**
- **产品成果**：在这个领域有没有做成过成功的产品？成果是什么、影响多大？
- **产品层面架构思考**：不只问技术怎么实现，而是问为什么做这个产品、解决什么人的什么问题、产品形态与架构如何相互影响。
- **行业思考**：行业里其他人/竞品怎么做？这个方向未来会怎么走？你的判断依据是什么？
- **开源参与**：有没有开源项目、提交、维护经历？社区影响力如何？
- **行业沉淀**：多年积累下来的方法论，而不只是项目清单。
- **通用解决方案**：能不能把具体项目中的做法**抽象成可复用的通用方案**，而不只是"我在 A 项目这么干过"。

**验收要点**
- 界面可选择 5 档难度。
- 高低档位的实际面试表现有可感知差异。

### FR-4 面试官提示词可自定义

**原始需求**
> 可设置面试官提示词，例如问基础知识为主，架构为主或项目为主等。

**需求描述**
- 可自定义"面试官提示词"，控制面试官的提问侧重方向。
- 典型侧重方向：基础知识为主、架构为主、项目为主等。
- 自定义提示词应能保存复用。

**验收要点**
- 面试配置时能填写/编辑面试官提示词。
- 不同提示词下，面试官提问的侧重方向确实不同。

### FR-5 预制面试官（国内大厂风格）

**原始需求**
> 预制几个面试官的提示词，比如字节面试官（侧重项目和知识深度）等。
> 预制国内常见四五个大厂的面试官（字节，阿里，百度，pdd，华为）联网搜索他们的风格并完成。

**需求描述**
- 内置 **5 套**大厂风格面试官提示词，开箱即用。
- 每套需体现该厂真实的面试风格（已联网调研，见下）。
- 与 FR-4 的自定义提示词是同一套机制，用户可在预制基础上修改另存。

**预制清单与风格定义**

#### 1. 字节面试官 — 项目细节刨根问底
- **核心特征**：简历上写的每一句都可能被刨到底，围绕技术选型理由连环追问。
- **典型追问链**：为什么选 Kafka 不选 RabbitMQ → 怎么保证消息不丢 → 消息堆积怎么处理 → 重新设计会怎么改。
- **关注点**：技术选型是否对比过其他方案、难点挑战如何解决、性能优化是否用数据说话、"流量翻十倍怎么办"。
- **风格**：节奏快、追问狠，不喜冗长回答；对"跟着教程做过但没深究原理"的项目会追到答不上来。
- **不考**：算法题（本项目不涉及代码题）。

#### 2. 阿里面试官 — 追问"为什么"，考工程判断力
- **核心特征**：本质是考**决策逻辑**而非知识验收，不断追问"为什么这么设计""极端情况怎么办"。
- **典型问题**："日活涨到 1000 万，架构怎么改"；答完原理继续追到具体实现细节（如"多线程并发写会怎样、哪行代码导致的"）。
- **关注点**：是否主动定义约束（流量是突发还是持续）、方案取舍的依据、项目中的技术难点与替代设计。
- **风格**：从项目切入 → 滚雪球式追问 → 考边界条件。堆砌技术名词不加分，讲清"为什么选 A 不选 B"才加分。
- **不考**：算法题。

#### 3. 百度面试官 — 重工程思维与代码质量
- **核心特征**：追问极细，连续追问如"如何保证不重发、不多发、不漏发"。
- **关注点**：评价维度是**可维护性 + 异常处理 + 扩展设计**，防御性编程与边界条件处理是重点；系统设计轮会追问"QPS 涨 10 倍代码哪里先崩""方案对业务延迟的影响"。
- **风格**：技术决策必须嵌入业务影响来讨论；问题密度大、拷打时间长。
- **不考**：算法题。

#### 4. 拼多多面试官 — 追到一个技术点讲不清为止
- **核心特征**：项目深追是常见翻车点，会持续追问技术决策理由（如"为什么不用本地缓存""缓存击穿雪崩怎么处理"）。
- **关注点**：一面重基础与项目，二面基本不问八股、改考开放性场景题（设计秒杀系统、海量数据去重、TOP K、大表 join 优化、分布式事务一致性）。
- **风格**：面试官态度普遍随和、答不上来会讲解，但**会追着一个技术点问到说不清为止**；节奏快、考察实、内容朴实。

#### 5. 华为面试官 — 极度重视项目经历
- **核心特征**：相比互联网大厂**不太深挖八股**，几乎全部问题从项目入手，极度重视实习与项目经历。
- **典型追问**：背景 → 方案 → 行动 → 结果逐项细问，追问创新点、难点、优化点、为什么这么做、有什么成果。
- **关注点**：底层原理追问（函数调用底层、TCP 拥塞控制、编译链接细节、智能指针/虚函数等）；主管面偏**抗压能力、团队分歧处理、稳定性与地点意向**。
- **风格**：面试官多数和蔼有耐心，但会"一路追问到答不出来才停"；主管面更严肃、有压迫感。

**验收要点**
- 面试配置页能看到 5 个预制面试官，各带名称与一句话风格说明。
- 选中不同面试官后，实际提问风格有可感知差异（如华为偏项目经历、阿里偏架构决策）。

### FR-6 面试总结评分（硬性要求：不迎合用户）

**原始需求**
> 有面试总结打分（一定不要迎合用户）给出具体真实的评价，给出具体的分数和建议。

**需求描述**
面试结束后生成一份总结报告，必须包含：
- **具体分数**
- **具体、真实的评价** —— 有依据、指名道姓，不能是放之四海皆准的套话
- **具体的改进建议** —— 可执行的下一步，而不是"多加练习"这类空话

**评分维度与权重**

| 维度 | 权重 | 说明 |
|---|---|---|
| 基础知识 | 20% | 技术概念、原理的掌握程度 |
| 项目回答 | 25% | 对自己项目的讲解深度，权重最高 |
| 解决问题能力 | 20% | 面对追问与难题时的分析与思路 |
| 知识深度 | 15% | 能否往下挖到原理、边界与取舍 |
| 知识广度 | 10% | 相关技术领域的涉猎范围 |
| 语言表达能力 | 10% | 表达是否清晰、有条理 |

**总分呈现**
- **百分制 0–100**。
- 同时给出明确结论：**推荐 / 待定 / 不推荐**。
- 并注明**按哪个职级标准评估**（对应所选难度档，如"按 L4 高级工程师标准"）。

```
总分  62 / 100      按 L4 高级工程师标准
结论  待定

维度得分
基础知识  ██████     58
项目回答  ████████   70
...
```

**L5 档的额外维度**
L5（行业专家/产品架构师）在六维之外**额外增加两个维度**：
- 产品与行业思考
- 行业沉淀与影响力

> L1–L4 使用固定六维，L5 使用八维。两者报告结构不完全一致，不做跨档位直接对比。

**硬性约束（本项目的核心价值）**
- **不得迎合用户**。禁止无依据的夸奖、鼓励性套话、为避免用户不适而抬高分数。
- 评价必须有依据，指向本次面试中的**具体表现**。
- 做得不好的地方必须明确指出来，不能含糊带过。
- 报告的呈现不应是"庆祝式"的。

**报告内容与存储**
- 报告需**写进报告**（含简历本身的问题，如措辞夸大、与答不上来的内容不符等，也应在报告中指出）。
- **不需要导出功能**，以 Markdown 形式存储即可。

**验收要点**
- 报告中有明确分值。
- 每条评价都能对应到面试中的具体回答，而非泛泛而谈。
- 故意答得很差时，必须给出低分和直白的负面评价，不出现鼓励性套话。
- 简历中夸大或含糊的措辞，应在报告中指出。

### FR-7 按住空格语音输入

**原始需求**
> 语音输入有键盘操作，按空格语音输入，松开则结束。

**需求描述**
- **按住空格键开始语音输入，松开空格键结束**（push-to-talk）。
- 界面上**另需一个可点击的语音输入按钮**，支持鼠标/触屏操作，与空格键等效。

**验收要点**
- 按住空格能开始识别，松开即结束，无需额外点击。
- 长按期间不因系统按键重复而异常。
- 在输入框内打字时，空格键仍是正常的空格输入，不被语音功能抢占。
- 按住期间切换窗口/切走标签页，不会出现"一直在录音"的状态。
- 点击界面的语音按钮同样能开始/结束语音输入。

**待确认**
- 错误提示形式（无麦克风权限、浏览器不支持等）。

## 三、非功能需求

| 类别 | 要求 |
|---|---|
| 运行方式 | 本地运行，单用户使用，不需要登录/账号体系 |
| 模型接入 | 必须可配置：支持本地模型（用户本机已装 Ollama + 千问），也支持通过 API Key 连接云端模型（如 DeepSeek） |
| 配置方式 | 模型配置在界面里完成，不要求用户改配置文件或重启服务 |
| 数据留存 | 简历、面试记录、评分报告需持久化，可回看历史 |
| 隐私 | 简历与面试数据保存在本地 |

## 四、已确认的决策

| 项 | 结论 |
|---|---|
| 技术栈 | React + Node.js 全栈 |
| 模型接入 | 统一走 OpenAI 兼容协议，可配置；本地 Ollama（千问）与云端 API Key（如 DeepSeek）都要支持 |
| 模型配置位置 | 界面设置页配置（含"测试连接"） |
| 语音识别方案 | 浏览器原生 Web Speech API，不引入云端 ASR |
| 面试官语音输出 | 不需要，纯文字 |
| 数据存储 | 后端 SQLite |
| 简历格式 | 仅 PDF，无粘贴文本兜底 |
| 报告导出 | 不需要导出，Markdown 存储 |
| 评分基调 | 真实、严格、不迎合 |
